## High findings

### R1. Connected CLI and stdio lack the Platform actor and credential rules

AD-10 assigns an operator-configured Actor to stdio and carries only availability and environment-binding checks into Platform-connected stdio. It assigns refusal of supplied Actor and derivation from authenticated identity to proposed HTTP. AD-13 requires short-lived hosted tokens but leaves the refresh store, lifetime and renewal proof unspecified. AD-14 describes an ordinary file with a `token` field. A team following those decisions could honor `--actor` on a connected CLI call or reuse the local profile for hosted refresh material. The Gateway still has its independent authorization duty. The connected clients would fail their own acceptance even if the Gateway refused every such call. **Evidence:** Spine 133, 145–147, 165–176, 406–407. Platform spine 135, 192, 383, 526. Platform epics 1942–1948 and 1960–1963 explicitly require local connected CLI and stdio to refuse actor or surface supplied by flag, environment or profile. Platform epics 2801–2819 requires staging OIDC, OS credential-store-only refresh material and no `offline_access`.

**Discuss with McpCli, Platform security and EventStore.** Bind identity policy to the selected environment for either head. Document the local development Actor exception, the connected Gateway’s authenticated-actor check and the staging credential lifecycle, including renewal or refusal at expiry. Add those cases to the connected acceptance row. The new HTTP transport continues to need its separate admission decision.

### R2. The run-scoped source build has no manifest input contract

AD-4 defines only a flagged `PackageReference` and a copy-local package asset. AD-17 describes a common candidate mapping and how to verify it in package mode. Neither identifies the build input that admits a Platform source-mapped Contracts assembly. The actual generator takes only `@(PackageReference)` plus copy-local paths and selects Assets by `NuGetPackageId`. With source-mapped output only, there is no matching package input to enroll. Selecting a same-version package to make that path work could run tests against different bytes. **Evidence:** Spine 74, 101–103, 184, 206, 283. `src/Hexalith.McpCli/Build/ModuleAssemblyManifest.targets:28–39,88–89`. Platform spine 109, 111, 123, 190, 383, 526 explicitly requires source-mode mapping, acceptance by assembly identity and candidate identity checks.

**Discuss with Platform/Builds and McpCli.** Define which mapped assembly identity and expected bytes the run-scoped generator consumes in source mode, who verifies them, and what rejects substitution or ambiguity. Exercise a source-built Contracts artifact and a same-version substitute. Keep the normal production tool’s flagged package manifest and restored-closure checks under AD-4/15.

### R3. Connected discovery has no shared public representation of executability

AD-3 defines conditions before *submission*, and accurately limits the shipped `submittable` field to local preflight. The connected open item also describes checks at execution. Neither gives the heads a compatible discovery response for a known local operation with a mismatched digest, or defines what happens when served metadata becomes stale. The exhaustive §G discovery records admit only `read_only` and `configuration_invalid` as reasons for a false `submittable`. A URL-configured head can therefore report local availability before refusing the call, while another head might hide the operation or emit an undocumented reason. All three could enforce the same submission guard. **Evidence:** Spine 95–97, 109, 159, 406. PRD 284–286 and Addendum 395–400, 409–413, 431. `src/Hexalith.McpCli.Core/Catalog/ExecutionAvailability.cs:3–10` and `src/Hexalith.McpCli.Core/Serialization/ResultDocumentSchema.cs:159–161`. Platform spine 188–191, 526 and Platform epics 1928–1940 require discovery to show mismatches as non-executable and offline inspection never to claim execution.

**Discuss with the PRD, Platform and EventStore owners.** Settle how callers distinguish local contract inspection from connected availability, how the public result expresses the latter, and how the client handles unavailable or stale Gateway metadata. Bind both heads and their output schemas to one Core decision. A useful acceptance case changes served eligibility or the digest while the local Contracts and URL stay fixed and compares the subsequent discovery and execution results.
