# PRD Quality Review — Hexalith.McpCli

Reviewed: `prd.md` (6,037 words) and `addendum.md` (757 words), against `.claude/skills/bmad-prd/assets/prd-validation-checklist.md`. Calibration: Internal stakes, developer product (MCP server plus CLI over a CQRS catalog), chain-top (feeds architecture, epics and stories, and a legacy-server migration plan), brownfield (six existing servers, four existing Contracts libraries). Brownfield claims were spot-checked against `references/` (contract interfaces, submission records, admin CLI conventions, module and project names); all checked claims were accurate.

## Overall verdict

This PRD has a real thesis (CQRS uniformity makes one generic agent surface possible, and the Decoration Attribute turns that into a platform policy), names its trade-offs honestly (replace over strangler, tool-as-identity in v1, Folders kept despite the largest prerequisite), and writes testable consequences for nearly every FR. It is good input for architecture and stories. What is at risk is a small set of internal contradictions that a story writer would implement faithfully and wrongly: FR-7 hides tenant-like properties from the Schema while FR-16 needs `TenantId` as the aggregate identifier for every Tenants command; `send_command` claims `idempotentHint: true` while the executor generates a fresh idempotency key per call and pushes retries to the caller; and neither FR-7 nor FR-15 says how the Catalog decides that a property is an identifier. The document is also roughly fifty percent over its length target, mostly through rules restated three or four times, which is the mechanism by which drift enters. Fix the five high findings and cut the duplication, and this is a safe spine.

## Decision-readiness — adequate

The PRD states decisions as decisions. §4.8 names the strangler-versus-replace trade-off and what was given up ("cross-repository coordination for six deletions after v1"). §6 "Identity in v1" is unusually candid: "The audit trail in the EventStore says 'the tool', not the human." §9.1's `[NOTE FOR PM]` on Folders sits at a real tension (the largest prerequisite is in another repository and the owner chose to keep it). The seven Open Questions are genuinely open; none answers itself in the next sentence, and each has an owner and mostly a revisit point.

Where it falls short is not smoothing but inconsistency: two places where the PRD has decided the same thing twice in incompatible ways. A decision-maker reading FR-9 would believe retries are safe; one reading FR-16 and §6 would know they are not. A decision-maker reading FR-7 would believe Tenants "needs no routing values" (FR-2) and works out of the box; the Schema rule in FR-7 breaks it. These are the kind of contradictions that only surface when someone builds the thing.

### Findings

- **high** Schema rule in FR-7 breaks the flagship module (§4.2 FR-7 consequence 2; §4.5 FR-16 consequence 4; §11 OQ3) — FR-7 says "The Envelope-supplied fields (Tenant, message identifier, idempotency key, correlation identifier) are not part of the Schema even if the record declares like-named properties." FR-16 says the aggregate identifier "comes from the `ICommandContract` instance property". In `Hexalith.Tenants.Contracts` every command is `record X(string TenantId, ...) : ICommandContract` with `AggregateId => TenantId`; Projects' `IProjectCommand` also declares `TenantId`. As written, the Schema hides `TenantId`, the validated Payload cannot populate it, and `AggregateId` resolves to null for the only module the PRD holds up as already routed. OQ3 acknowledges the question but FR-7 has already committed to the answer that fails. *Fix:* Replace FR-7 consequence 2 with a neutral statement ("Envelope-only fields the record does not declare are not added to the Schema; how declared tenant-like properties are treated is OQ3, decided before FR-7 is implemented") and add to OQ3 the concrete Tenants case so architecture sees the constraint: the property is simultaneously the aggregate identifier and the tenant.
- **high** `idempotentHint: true` contradicts the per-call key and the caller-retries rule (§4.3 FR-9 consequence 8; §4.5 FR-16 consequence 1; §4.5 FR-17 consequence 4; §6 Idempotency) — FR-9 marks `send_command` idempotent "because the tool generates an idempotency key per call and the Gateway honours it." FR-16 then requires "Two identical calls produce two different message identifiers and idempotency keys", §6 says "a caller cannot supply either", and FR-17 says "retries belong to the caller; an agent can decide." Under MCP semantics `idempotentHint` means repeating the call with the same arguments has no additional effect; here a repeat creates a second command. The Gateway's idempotency key is being generated in the one place that defeats it, and the agent that is told to decide on retries has no safe way to retry. *Fix:* Decide one of: (a) `idempotentHint: false`, and either the executor retries retryable Gateway errors reusing its own key, or the result returns the key and `send_command` accepts an optional caller-supplied idempotency key (ULID) for a replay; or (b) keep the caller out but let the executor own retry with a stable key. Update FR-9, FR-16, FR-17, and §6 together; delete the FR-9 assumption.
- **medium** v1 acceptance is coupled to Folders readiness without saying so (§9.1 Named prerequisites; §10 SM-1; §4.8 FR-20) — FR-20 says a Module that is not Gateway-ready "appears with zero Operations and a startup diagnostic", which implies v1 can ship with three live Modules, but SM-1 requires all four "exposed" and §9.1 says "v1 is only useful once each of the four Modules is Gateway-ready." A reader cannot tell whether v1 waits for Folders. *Fix:* One sentence in §9.1: whether v1 ships when Tenants and Parties are Gateway-ready (with Projects and Folders following) or waits; adjust SM-1's wording to match.
- **low** OQ4 is half-answered by FR-22 (§11 OQ4; §4.8 FR-22) — FR-22 already rules that no new "per-module agent CLI" is created; OQ4 asks "whether the no-new-server rule covers them." Only the deletion half is open. *Fix:* Narrow OQ4 to "are the five existing per-module CLIs deletion targets, and on what parity bar."

## Substance over theater — adequate

There is very little furniture. There is no persona section; §2.1 uses jobs-to-be-done, and the two named protagonists (Nadia, Marc) each carry an edge case that lands on an FR (validation error naming the property → FR-11; undescribed record excluded and logged → FR-6). The Vision could not swap into another PRD: "A Command without a description is a Command an agent cannot use" is this product's sentence. NFRs carry thresholds (500 ms, 2,000 tokens, byte-identical output) rather than adjectives, and NFR-8 admits it is review-verified rather than pretending otherwise.

What reads as furniture is repetition, not invention. The same rule appears in three to five places in slightly different words, and §7 "Runtime targets" is duplicated verbatim in addendum §B. At 6,037 words against a five-to-eight-page target (roughly 2,500–4,000 words), the excess is almost entirely restatement plus mechanism detail that belongs in the addendum.

### Findings

- **high** Overlength through restatement; concrete cuts (whole document) — Rules restated: dependency policy appears in §1, FR-1 c4, FR-5 c1, FR-20 c2, §6, §7, §8 last bullet, SM-1, SM-C3 (nine places); tenant-from-Envelope in Glossary, FR-7 c2, FR-16 c2, §6; ULID in FR-7, FR-15, §6; read-only "four tools" in FR-9 c1 and FR-19 c1 plus §4.7 description and §6; the five tool names in Glossary, FR-9, FR-12, §7, §9.1; plugin loading, typed tools, and generated subcommands in both §8 and §9.2; admin plane and HTTP transport in §2.2, §6, §8, §9.2. Each restatement is a place for the next edit to miss. *Fix:* Keep each rule in exactly one authoritative place (§6 for guardrails, the owning FR for behaviour) and cross-reference by FR number elsewhere. Move to addendum §B: FR-9's per-tool argument lists (keep a one-line contract per tool in the PRD, put the argument table in the addendum), FR-12's payload input forms, FR-13's environment-variable names and precedence fixture, FR-18's file schema details, and delete §7 "Runtime targets" (already in addendum §B). Collapse §2.2 to one line pointing at §8. Drop the §9.2 bullets that only repeat §8 (plugin loading, typed tools, generated subcommands), keeping those with a release timing. Estimated saving 1,200–1,500 words with no lost decision.
- **medium** FR-21 and FR-22 are policy and migration requirements dressed as tool FRs (§4.8) — FR-22's deliverable is an edit to `hexalith-llm-instructions.md` in Hexalith.AI.Tools; FR-21's deliverable is a per-server parity table in the migration plan. Neither produces code in this repository, and a story generator will emit stories for them alongside "derive a JSON Schema". FR-21 is also in neither §9.1 nor §9.2 as an in-scope item (§9.2 references it only to defer deletions). *Fix:* Move both into a short "§4.8 Migration and policy commitments" block that is explicitly marked as non-code (or into §9 as named prerequisites and follow-ups), keep their consequences, and state in §9.1 that the parity table is a v1 deliverable if it is.

## Strategic coherence — strong

The thesis is stated in §1 and everything hangs off it: uniformity of CQRS through one Gateway → one generic surface → decoration as a policy → no new per-module server. Feature order follows the thesis (decoration, catalog, heads, executor) rather than ease. Success Metrics validate the bet rather than activity: SM-1 (zero module-specific code, fifth module by package reference) and SM-2 (cross-module task through five tools only) are the thesis in test form. Counter-metrics are real and pointed at the temptations this product will face: SM-C2 "do not chase task success by adding typed tools" and SM-C4 against hollow descriptions. MVP scope kind is platform, and §9 reads as platform scope.

### Findings

- **medium** No metric for the audience the thesis is about (§10 vs §1 and §2.1) — The brief and §2.1 say the bet is that "Hexalith's own Agents, ChatBot, and Conversations modules will soon need to act on business data." UJ-2's protagonist is a Conversations agent. No SM measures whether any of those three integrates the server; SM-2 can be satisfied by Claude Code alone. *Fix:* Add a secondary SM, "at least one of Agents, ChatBot, Conversations reaches Hexalith business data through the Generic Tools", or state in §10 that first-party module adoption is deliberately not a v1 metric.

## Done-ness clarity — adequate

Most FRs would let an engineer know what done looks like: FR-5's byte-identical ordering, FR-10's "a test that pipes stdout into an MCP client parser sees only valid JSON-RPC frames", FR-15's "the test double for the Gateway client records zero calls", FR-16's ULID checks, FR-19's hand-crafted-request refusal. This is above the bar for Internal stakes. The gaps are specific rules the FRs assume without stating, and two places where the same flag or exit code means two things.

### Findings

- **high** No rule for what counts as an identifier (§4.2 FR-7 consequence 1; §4.5 FR-15 consequence 3) — FR-7: "identifiers are typed as strings with a ULID pattern"; FR-15: "Identifier fields are validated with `Ulid.TryParse`". Nothing says how the Catalog recognises an identifier: by property name suffix `Id`, by a marker attribute, by a known type? `Hexalith.Projects.Contracts` uses a strongly typed `ProjectId ProjectId`; Tenants uses `string TenantId`; Parties uses plain strings. Without the rule, the Schema and the validator cannot be written, and `Name` versus `NameId` will be argued in a story. *Fix:* State the rule (recommended: a property whose type is a known identifier type or whose name ends in `Id`, overridable by a Decoration Package attribute) and add an explicit negative consequence ("a string property not matching the rule is not ULID-validated").
- **medium** Exit code 1 has no trigger a script can predict (§4.4 FR-14) — "1 when the Operation was accepted with a warning" plus the assumption "a Catalog that started with excluded records" means every `modules` or `send` invocation exits 1 while any upstream record is undescribed, which will break `set -e` scripts for reasons unrelated to the call. *Fix:* Enumerate the exit-1 triggers (recommended: Gateway responses that are accepted-with-warnings only; Catalog diagnostics are stderr-only unless `--strict`) or drop exit 1 for v1 and reserve it.
- **medium** `--strict` means two different things (§4.1 FR-4 consequence 2; §4.2 FR-6 consequence 3) — On `describe`, `--strict` reports undescribed properties; at startup, `--strict` turns any diagnostic into a failure. One word, two behaviours, and FR-4 never says whether `describe --strict` changes the exit code. *Fix:* Rename one (for example `describe --lint`) and state the exit code for each.
- **medium** Aggregate identifier rule covers Commands only (§4.5 FR-16 consequence 4; §4.3 FR-9 `run_query`) — `SubmitQueryRequest` requires an `AggregateId`, and `run_query` accepts "an optional aggregate identifier", but FR-16's resolution order and its failure case are written "for a Command". Queries with no natural aggregate (list and search queries) have no stated behaviour. *Fix:* Add one consequence for Queries: where the aggregate identifier comes from (`IQueryContract` has none), and what the Envelope carries when there is none.
- **low** Conflict between payload property and explicit argument is unspecified (§4.5 FR-16 consequence 4) — The order "interface property, else attribute-named Payload property, else explicit `aggregateId`" does not say what happens when both are present and disagree. *Fix:* One clause: disagreement is a validation failure.
- **low** Small unbounded phrases (§4.3 FR-11 c4; §5 NFR-2; §5 NFR-7) — "the nearest Operation Names by edit distance" (how many); "under 2,000 tokens" (which tokenizer); "integration tests against a running EventStore" (how CI gets one). *Fix:* "up to three"; "measured with the Claude tokenizer" or "under 8,000 characters"; name the harness (Aspire, container) or defer to architecture explicitly.

## Scope honesty — strong

§8 Non-Goals does real work ("Not a second executor: the tool never calls a Module's REST or Dapr API" is the sentence that keeps four legacy servers alive until their modules migrate, and it is stated rather than implied). De-scoping is done in the open: §9.2 lists seven deferrals with timing, and the two `[NOTE FOR PM]` callouts in §9 sit on load-bearing deferrals (Folders prerequisite; HTTP transport gating per-user identity). Nineteen inline `[ASSUMPTION]` tags, three `[NOTE FOR PM]`, seven Open Questions: for Internal stakes on a green-light PRD this density is acceptable, and most assumptions are defaults with a fallback rather than unknowns. The one assumption that hides a decision is FR-1's analyzer, and it is correctly surfaced as OQ6.

### Findings

- **high** Decoration Package home and release ordering are undecided but load-bearing (§7 Public surface; §9.1 Named prerequisites; §11 OQ7) — Four upstream Contracts Libraries must reference the Decoration Package before this repository can reference their new versions, so there is a two-way release dependency between this repository and every Module. The PRD says the package "references no other package" but never says where it lives (this repository, `Hexalith.EventStore.Contracts` next to `ICommandContract`, or `Hexalith.Commons`), or that it must be published before any upstream prerequisite can start. OQ7 covers names only. The epic order, the migration plan, and "a Contracts Library must build unchanged across minor versions" all depend on this. *Fix:* Add to OQ7 (or decide now) the package's home repository and feed, and add to §9.1 a first prerequisite: "the Decoration Package is published before upstream decoration begins." If the home is `Hexalith.EventStore.Contracts`, restate FR-1 consequence 4 accordingly.
- **low** Tenant override as a tool argument is a fourth source (§4.3 FR-9 `send_command`, `run_query`; §6 Tenant) — §6 lists "Profile, flag, environment variable, or, next release, forwarded header"; FR-9 adds a per-call "optional Tenant override" supplied by the agent. It is consistent with "never from the Payload" but not with the §6 list. *Fix:* Add "per-call tool argument" to the §6 list and to FR-13's precedence order.

## Downstream usability — strong

The Glossary is used with discipline: Module, Contracts Library, Operation, Operation Name, Catalog, Head, Envelope, Tenant, Profile, Read-only Mode, Legacy Server, Gateway-ready are capitalised and used identically across FRs, UJs, and SMs. IDs are contiguous (FR-1..22, NFR-1..8, SM-1..6, SM-C1..4, UJ-1..3) and every cross-reference resolves (FR-1→FR-6, FR-7→OQ3, FR-8→FR-6, FR-14→FR-11, FR-16→FR-2, §9.2→FR-21, OQ6→FR-1, every "Realizes UJ-n" and "Validates FR-n"). Each §4 cluster reads alone. UJ-1 and UJ-3 have named protagonists; UJ-2's protagonist is a software agent, which is right for this product. The addendum is properly separated and points back to the brief rather than duplicating it. No findings beyond the mechanical notes.

## Shape fit — strong

Internal developer product with one operator role, chain-top, brownfield: the PRD chose capability-spec shape with three light journeys and cross-cutting NFRs, which is the right shape. Brownfield references were checked and are accurate: the six named Legacy Servers exist under `references/`; `ICommandContract` has static `CommandType` and `Domain` and instance `AggregateId`; `SubmitCommandRequest` carries `CorrelationId`, `Extensions`, `IdempotencyKey`; the admin CLI uses `EVENTSTORE_ADMIN_URL|TOKEN|FORMAT`, exit codes 0/1/2 (`Degraded = 1`), and profile store version 1 at `~/.eventstore/profiles.json`; `Hexalith.Folders.Contracts` has no command or query records. The one shape blemish (FR-21, FR-22 as tool FRs) is filed under Substance. No further findings.
