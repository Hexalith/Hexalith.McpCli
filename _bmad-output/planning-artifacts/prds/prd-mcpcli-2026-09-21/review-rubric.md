# PRD Quality Review — Hexalith.McpCli

Reviewed 2026-09-22: `prd.md` (6,284 words, status final, amended 2026-09-22 from `ARCHITECTURE-SPINE.md`) and `addendum.md` (1,521 words), against `.claude/skills/bmad-prd/assets/prd-validation-checklist.md`. Calibration: Internal stakes, developer product (generic MCP Server plus CLI over a CQRS Command/Query Catalog), chain-top (feeds architecture, epics and stories, legacy-server migration), brownfield. This is a fresh judgment on the current text; the 2026-09-21 review was read only to track which of its findings still stand (see "Prior findings" at the end). Brownfield claims were spot-checked under `references/` (EventStore contracts, validators and router; Tenants, Parties, Projects, Folders, Memories); results are stated inline where they change a judgment.

## Overall verdict

The amended PRD is a sound spine: the thesis (CQRS uniformity through one Gateway makes one generic agent surface possible, and the Decoration Attribute turns that into a platform policy) still drives every feature, the four contradictions the first review found are gone, and nearly every FR carries a consequence a story can test. What is at risk is one open question the PRD treats as safely deferred but is not: the Gateway's query validator rejects an empty `AggregateId`, so FR-16's interim rule for list-style Queries fails against the referenced code on the first Tenants query story; and one brownfield claim (`projectionActorType` for Tenants) is stale. Resolve OQ-3 before the executor stories and re-verify the Tenants query routing, and this PRD can be built from without further amendment.

## Decision-readiness — strong

Decisions are stated as decisions with what was given up: §5.7 "replacement over a strangler pattern to remove the inconsistency for good, accepting cross-repository coordination"; §4 "Identity in v1" says the audit trail "says 'the tool', not the human" and names that as the reason the HTTP transport is next; §8 makes the v1 gate explicit ("v1 is done when the tool is released and Tenants and Parties are covered end to end") rather than letting Folders sit on the critical path. The four remaining Open Questions (OQ-1, OQ-3, OQ-5, OQ-6) are genuinely open, each with an owner and a revisit point, and the three resolved ones say where they were resolved and keep their numbers. The two `[NOTE FOR PM]` callouts (§8.1 Folders, §8.2 HTTP transport) sit at real tensions.

The one place a decision is shown as open after it was made elsewhere is Tenants paging (finding below). Everything else a pushing-back reader would raise (typed tools, strangler, OAuth, retries) is acknowledged in §8.2, §8.3, or the addendum.

### Findings

- **medium** Tenants paging decision is still shown as open although the spine decided it (§8.1 Tenants prerequisite; FR-7; FR-17; addendum §E) — §8.1 says "decide whether the `Cursor` and `PageSize` Payload members give way to Envelope paging", but the spine's AD-20 ("Paging is Envelope-only") already decided, and the 2026-09-22 amendment pass did not carry it into the PRD. As written, FR-7 puts `Cursor` and `PageSize` in the Schema ("includes every declared property") while addendum §E offers `pageSize`/`cursor` as tool arguments, so an agent calling `tenants.get-user-tenants` sees two paging channels and the PRD does not say which wins. `GetUserTenantsQuery` and `GetGlobalAdministratorsQuery` in `references/Hexalith.Tenants/src/Hexalith.Tenants.Contracts/Queries/` carry both members today. *Fix:* Record AD-20 in the PRD (one consequence under FR-16 or FR-17: paging travels in the Envelope only; Payload paging members are ignored or rejected, pick one) and turn the §8.1 Tenants bullet into a prerequisite ("remove or ignore `Cursor` and `PageSize` on Query records") instead of a decision to make.

The Vision is this product's and no other's: "a Command without a description is a Command an agent cannot use". NFRs carry bounds (500 ms, 8,000 characters, byte-identical output, `LoggerMessage`), and NFR-3/4/5 are honest pointers rather than restated adjectives. The addendum keeps mechanism, comparables, and the argument table out of the requirements.

The growth is legitimate (amendments), and the restatements that remain are mostly one-line pointers, so the drift risk the first review named is much reduced.

## Done-ness clarity — adequate

Most FRs give an engineer a done condition: FR-5 byte-identical output; FR-10 an SDK-driven stdio round trip; FR-14's exit-code table; FR-15 "the substituted Gateway client records zero calls"; FR-16 ULID checks and the accessor rule; FR-19 hand-crafted request refusal. The Identifier Kind, accessor, and readOnly-property rules from the amendment close the gaps that mattered most. What remains is one stated fallback that fails against the referenced Gateway, and one interplay between lint findings and exit codes that will surprise scripts.

### Findings

- **high** FR-16's interim rule for aggregate-less Queries is rejected by the Gateway today (FR-16 c2 `[ASSUMPTION: a Query with none sends an empty aggregate identifier pending OQ-3.]`; §10 OQ-3; §5.1 table `aggregateIdProperty` "optional for a Query") — `references/Hexalith.EventStore/src/Hexalith.EventStore/Validation/SubmitQueryRequestValidator.cs` has `RuleFor(x => x.AggregateId).NotNull()...NotEmpty().WithMessage("AggregateId cannot be empty")`, and `SubmitQueryRequest.AggregateId` is a non-nullable `string`. So every Query without an aggregate identifier source (`ListTenantsQuery`, `GetGlobalAdministratorsQuery`, and any Parties list Query created for §8.1) would fail Gateway validation under the PRD's own fallback, and UJ-2's "result comes back paged with a cursor" cannot be demonstrated on the first Module until OQ-3 is answered. The PRD presents this as a deferrable open question with a working interim; it is a blocker for the executor and Query stories. *Fix:* Promote OQ-3's revisit point from "before FR-16 is implemented" to "before the Executor epic starts" and state the constraint in the OQ ("the Gateway validator requires a non-empty `AggregateId`; candidates: a conventional sentinel such as the Tenant, a `ProjectionType`-scoped key, or a Gateway change"). Replace the FR-16 assumption with "a Query resolving to no aggregate identifier is `validation_failed` until OQ-3 is resolved" so the interim behavior is at least honest and testable.
- **medium** Undescribed properties make every discovery verb exit 1 until Modules are fully described, and the three lint categories are placed inconsistently (FR-4; FR-6 warning categories; FR-7 c4; FR-14 exit 1) — FR-6 lists "undescribed property" as a startup warning (type kept) reported on stderr; FR-14 says exit 1 is "Result document produced, and a diagnostic was written to stderr for this invocation (discovery verbs and `describe --lint` only)". Zero `[Description]` attributes exist in the Tenants or Parties Contracts today (verified), so `hexalith modules` and `hexalith operations tenants` will exit 1 on every run under `set -e` until the last property is described, and with `--strict` (FR-6 c3) `send` and `query` will refuse to start. Meanwhile FR-7 c4 makes the unmarked-`Id` case "a `describe --lint` warning" only, not a startup diagnostic. One lint finding is a startup warning that degrades exit codes; the other is lint-only; the PRD does not say why. *Fix:* Decide one model and state it in FR-6: either (a) property-level findings (undescribed property, unmarked identifier-like property) are lint-only, surfaced by `describe --lint` and never at startup, so discovery verbs exit 0 while the Catalog is usable; or (b) they are startup warnings, in which case say explicitly in FR-14 that discovery verbs exit 1 while any Module has an undescribed property and that CI scripts should use `--strict` or `--format json` with exit-code tolerance. (a) matches FR-14's intent that Catalog diagnostics do not degrade normal use.
- **low** A Query with no Tenant has no stated outcome (FR-13 c4) — "A Command with no Tenant from any source is a validation failure." `SubmitQueryRequest.Tenant` is required and the Gateway validator rejects an empty one; the PRD says the only tenant-less Queries are undecorated in v1 but never states what happens to a decorated Query with no Tenant. *Fix:* "A Command or Query with no Tenant from any source is a validation failure."
- **low** Duplicate Module Name is a "startup error" in FR-3 and an exclusion category in FR-6; which assembly survives is unstated (FR-3 c2; FR-6 error categories) — FR-6's error categories are defined as "type excluded", but a duplicate Module Name is an assembly-level conflict. *Fix:* One clause in FR-3: both assemblies are excluded (or the first by sorted assembly name wins) and the diagnostic names both.

De-scoping is in the open: Folders is kept in the v1 Module list but explicitly does not gate v1 (FR-20, §8.1 `[NOTE FOR PM]`). Open-items density is right for Internal stakes on a green-light PRD: 10 inline `[ASSUMPTION]` tags, 2 `[NOTE FOR PM]`, 4 open OQs, and most assumptions are defaults with a fallback rather than unknowns. The exception is the FR-16 assumption, filed under Done-ness above. No further findings.

## Shape fit — strong

Internal developer product with one operator role, chain-top, brownfield: capability-spec shape with three light journeys, cross-cutting NFRs, a public-surface section, and named per-Module prerequisites is the right shape, neither over- nor under-formalized. Brownfield references checked in this pass and found accurate: `ICommandContract` has static `CommandType` and `Domain` and an instance `AggregateId` getter (FR-2, FR-16); `IQueryContract` has static `QueryType`, `Domain`, `ProjectionType` and no actor type (§5.1 table); `SubmitCommandRequest` and `SubmitQueryRequest` field lists in addendum §B are exact; `ConnectionProfile(Url, Token, Format)` has no extension member (§5.6); Tenants is the only `ICommandContract`/`IQueryContract` implementer, uses kebab-case `CommandType`, routes global-administrator Commands to `TenantIdentity.GlobalAdministratorsDomain` (FR-2 c4), and uses the plain string `system` as a tenant identifier (FR-3 c3); `Hexalith.Tenants.Contracts` and `Hexalith.Parties.Contracts` reference only `Hexalith.EventStore.Contracts` (closure rule passes, FR-20); `Hexalith.Projects.Contracts` references `FrontComposer.Shell`, `Fluxor.Blazor.Web`, and `Microsoft.AspNetCore.App` (closure rule fails, FR-20 c3); Projects command records carry `TenantId`, `CorrelationId`, `IdempotencyKey` and `CommandType => nameof(...)` (§8.1 Projects); Parties has 24 Command records and no Query types (§8.1 Parties); `Hexalith.Folders.Contracts` holds projections and OpenAPI only and `Hexalith.Folders.Mcp` declares 49 tools (§8.1 Folders); `Hexalith.Memories.Mcp` references `JwtBearer` (FR-21 c3); `McpContextForwardingHandler` sets `X-Tenant-Id` and `X-User-Id` (addendum §B). Not verified in this pass: the Parties legacy server's `domain = "party"` and full-CLR-name Wire Type (its request construction was not located cheaply), and the "11 resources" count for Projects.

### Findings

- **medium** The Tenants projection-actor claim looks stale (§5.1 table row `projectionActorType`: "Module has its own projection actor (Tenants)"; FR-2 c1 "A Tenants Query still needs `projectionActorType`"; §8.1 Tenants prerequisite) — `references/Hexalith.Tenants/src/Hexalith.Tenants/Queries/Handlers/TenantQueryHandlerBase.cs` describes the "retired `TenantsProjectionActor`" and says reads go through `IReadModelStore` via in-process `IDomainQueryHandler` dispatch, and the Gateway's `HandlerAwareQueryRouter` routes a query to the domain handler endpoint whenever the registry supports it, without a projection actor. The PRD's claim matches the doc comment on `SubmitQueryRequest.ProjectionActorType` ("domain services with their own projection actor (e.g., tenants)"), which the Tenants code has outgrown. No `ProjectionActorType` string appears anywhere in the Tenants sources. If Tenants Queries are handler-routed, the `projectionActorType` member is not a Tenants prerequisite and FR-2 c1 sets a false test. *Fix:* Confirm with the Tenants owner. Then either drop the Tenants example and make `projectionActorType` "optional; only for a Module whose Gateway queries are served by a dedicated projection actor", or, if Tenants still needs it on the Gateway path, cite the actor type name so the consequence is testable.
