Hexalith.McpCli PRD — Validation Report

_bmad-output/planning-artifacts/prds/prd-mcpcli-2026-09-21/prd.md (+ addendum.md)
Poor

The amended PRD is a sound spine: the thesis (CQRS uniformity through one Gateway makes one generic agent surface possible, and the Decoration Attribute turns that into a platform policy) still drives every feature, the four contradictions the 2026-09-21 review found are gone, and nearly every FR carries a consequence a story can test. What is at risk is one open question the PRD treats as safely deferred but is not: the Gateway's query validator rejects an empty AggregateId, so FR-16's interim rule for list-style Queries fails against the referenced code on the first Tenants query story; and one brownfield claim (projectionActorType for Tenants) is stale.

The adversarial and spine-alignment reviewers materially shift the picture, and their critical findings were spot-checked against the source under references/. Three brownfield facts contradict the PRD as written: Tenants runs every Command and Query under the fixed Envelope tenant system, so the one-default-tenant-per-Profile model and FR-13's "tenant-less global-administrator Queries" claim are wrong for the flagship Module; Hexalith.EventStore.Contracts package-references Hexalith.Commons.UniqueIds, so the §4 closure rule and its CI test reject both v1 Contracts Libraries on day one; and SubmitQueryRequest carries neither a correlation identifier nor extensions, so FR-16 and addendum §E promise a run_query pass-through the pinned client cannot make. A fourth critical is a design gap: the LLM-controlled per-call tenant argument, identity-bearing Payload properties such as Projects' ActorPrincipalId, and unrestricted extensions are three caller-controlled identity paths the §4 tenant guardrail does not cover. The grade is Poor because of these blockers, not because of the document's craft; the PRD is usable now for the Decoration Package, Catalog, MCP head, CLI head, and Profile epics, and becomes usable for the executor and coverage epics once the four criticals and the OQ-3 decision land.

Adversarial review

review-adversarial-general.md

The PRD is well-structured and most of its mechanism is decided, but it is built on a tenancy model that the flagship v1 module does not follow, a dependency rule that excludes the two modules it names, and a read path that no existing code exercises. On security, the PRD lets an agent set the envelope tenant per call, pass arbitrary extensions, and write identity-bearing payload properties, which together are an impersonation path the guardrails do not cover. Six months out, the most likely failure is a tool that can write but not read, holds a platform-administrator token on a developer laptop, and exposes a Catalog whose upstream decoration work nobody scheduled. Ship only after the critical findings are resolved; the high findings should be decided before stories are cut. Counts: 4 critical, 11 high, 12 medium, 6 low. The four criticals were spot-checked against source by the validating session and hold.

critical

C-1. Tenants runs under the fixed Envelope tenant system; the PRD's tenant model cannot drive it

§3 Tenant; §4 Tenant; FR-3 c3; FR-13 c4; FR-18; UJ-1; UJ-2
TenantIdentity.ForTenant(managedTenantId) yields Envelope tenant system with the managed tenant as aggregate id; TenantsSystemTenantValidator and GetGlobalAdministratorsQueryHandler reject anything else. FR-13's "tenant-less" claim is false, FR-3's rationale conflates Envelope tenant with Identifier Kind, UJ-1 and UJ-2 cannot share one Profile default tenant, and nothing in describe_operation tells the agent to pass tenant: "system". A token with the system claim is a platform-administrator token on a laptop.
Fix: Add a Module marker member fixedTenant (or an Operation member tenant) surfaced by describe_operation as the Envelope default and used by the executor when no per-call tenant is given; a differing per-call tenant is validation_failed. Rewrite FR-3 c3 with a real non-ULID aggregate id; fix FR-13 c4 and both journeys.
critical

C-2. The closure rule as written excludes Tenants and Parties themselves

§4 Dependency policy; FR-20; §8.1 Projects; addendum §B; spine AD-15
Hexalith.EventStore.Contracts.csproj package-references Hexalith.Commons.UniqueIds, which references ByteAether.Ulid. "No other Hexalith package" therefore fails for every Contracts Library, the CI test blocks the first v1 pin, and the first story will loosen the rule ad hoc, which is how Hexalith.Projects.Contracts grew Fluxor and FluentUI. Hexalith.Parties.Contracts already ships service interfaces; "Contracts" is a package name, not a purity guarantee. The spine reviewer rates the same finding high.
Fix: State the rule once in §4 as an allowlist: *.Contracts packages, Hexalith.EventStore.Contracts and its own transitive closure at the pinned version, no framework reference beyond Microsoft.NETCore.App; additions are a PRD change. Point §3 and FR-20 at §4; align AD-15.
critical

C-3. Identity can be set by the caller three ways; the tenant guardrail covers none of them

§4 Tenant; FR-9 argument table (tenant, extensions); FR-16; FR-21 c2; §8.1 Projects
(1) The per-call tenant argument is chosen by the LLM; a token with several tenant claims lets the agent hop tenants per call with no operator consent, a fourth tenant source the repository policy does not list. (2) Projects' IProjectCommand.ActorPrincipalId is an ordinary Schema property, so send_command lets the agent name any principal as the actor and the audit trail records it. (3) --extension key=value passes through with no allowlist against a Gateway whose ITrustedCommandExtensionPolicy stores unclaimed keys as trusted.
Fix: Honor per-call tenant only when the Profile has no default or the operator sets --allow-tenant-override, else validation_failed. Add an actorProperty attribute member the executor fills from session identity and marks readOnly. Add a per-Profile extension-key allowlist, default empty.
critical

C-4. run_query has no proven path for either v1 module, and the PRD's fallback is rejected by the Gateway

FR-16 assumption; OQ-3; §5.1 projectionActorType; §8.1 Tenants and Parties; FR-20
Same root as the Done-ness critical above, plus: Tenants query handlers are reached today through REST routes, and Parties, the only Module that reaches the Gateway at all, has no Query types. "Tenants and Parties covered end to end" rests on a read path that nothing exercises.
Fix: Promote OQ-3 to a v1 blocker with a named owner and a spike deliverable; add a fixedAggregateId attribute member for list-style Queries; replace the empty-identifier assumption with validation_failed.
