## High — The proposed HTTP credential flow conflicts with adopted K10

PRD §8.2, line 526, calls for bearer, tenant and user header forwarding. Addendum §B, lines 90–92, specifically directs implementers to reuse the Parties forwarding handler. That handler copies the inbound Authorization header to the outgoing request and adds tenant and user headers. The approved K10 decision requires token exchange, authenticated actor and effective-origin attestation, issuer/audience/client mapping and denial evidence, and explicitly prohibits raw user-token forwarding. The original brief predates this decision. Transcribing its design could pass an operator’s credential across a service boundary that requires an exchanged credential.

Keep per-user authority as the product goal. Give OQ-1 the adopted identity constraints and identify the Parties implementation as historical context. Architecture and security owners still have to approve the concrete HTTP design. The current stdio transport has its own credential rules. ## Medium — The parity exclusion can waive required handler behavior

Addendum §F, lines 318–322, groups search, filters, ordering and freshness under “excluded from parity”. FR-9 at line 288 limits its exclusion to generic `run_query` arguments. FR-21 at line 446 and adopted K03 require evidence for the approved Module Payload and handler semantics, including filtering before paging and continuation contents. The approved Parties T03 replacement explicitly requires corrected search and filtering. An inventory reviewer following §F alone could close migration parity on a missing filtered result.

Limit §F’s exclusion to dedicated generic arguments and HTTP features. State that each included Module replacement still owes its approved filtering, freshness and pagination evidence under FR-21/K03.
